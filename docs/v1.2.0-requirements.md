# V1.2.0 需求分析草案

> 本文保留实现前的需求分析记录。后续已按交互草稿在本地实现，采用“每次完整启动时登录、成功后不持续重连”的规则。实现与验证结果见 [本地验证记录](v1.2.0-verification.md)。

本阶段只明确目标和验收口径，不实现功能，不修改版本号，不构建或发布。以下“建议”是待确认的产品规则，不代表用户已经确认。

## 一、现状与问题

当前版本为 1.1.0。结合源码和使用说明确认：

- 本地仅保存一组账号密码；保存不会直接登录。
- 后台循环检查网络并在离线时重新登录；主动断开通过暂停状态阻止重连。
- 休眠恢复、凭据错误、在线账号不一致等情况也影响自动登录状态。
- 已经可以不依赖本地凭据查询校园网状态，但界面没有清楚区分凭据与在线身份，侧栏还会回退显示检测到的在线账号。
- 账号管理位于设置页较下方，没有首次使用引导。
- 当前登录流程遇到其他账号在线会拒绝登录，因此多账号切换需要新增真正的注销、认证和验证流程。

## 二、产品中的三个独立概念

1. **已保存账号**：软件在本机保存了账号和密码，可以用于提交认证。
2. **当前选用账号**：用户选定供手动登录及下次启动登录使用的账号。
3. **当前在线账号**：校园网接口报告的本机实际登录身份。

三者不能互相推定。网络在线不表示保存过密码；保存凭据不表示认证成功；当前选用账号也可能暂时与在线账号不同。接口无法确定在线身份时，应显示未知，不能以选用账号补全。

## 三、功能目标

### 1. 多账号管理与实际切换

这里的多用户指同一 Windows 用户下保存和切换多个校园网账号，不涉及注册系统、角色权限或云端账号。

- 可以添加、编辑、删除多个账号，并明确标示当前选用账号。
- 同一学工号建议作为同一条记录管理，避免重复添加。
- 密码继续在本地加密保存，前端不回显已保存密码；新增账号必须填写密码。
- “切换并登录”必须更换实际网络认证身份，不能只更新界面或本地选中项。
- 在线 A 切换到 B：检查当前状态 → 注销本机 A → 确认已离线 → 用 B 认证 → 查询并确认在线身份为 B。
- 已离线则直接认证 B；已确认本机在线账号为 B，则无需先断开重登。
- 切换时串行处理网络操作，避免后台登录或旧请求把账号切回 A；旧账号统计与设备数据不得在新账号下展示。
- 注销失败则不继续认证 B；B 认证失败则如实显示实际网络状态与失败原因，不宣称切换成功。
- 建议将 B 保留为选用账号，失败后允许重试，不自动登录回 A。网络请求超时后应重新查询实际状态，再判断结果。
- 明确点击切换才执行账号替换；启动检测到其他账号在线时，建议只提示差异，保留已有连接。
- 只处理本机连接，不为切换主动下线其他设备。
- 旧版单账号自动迁移为第一条账号记录，保留凭据和原设置意图。

建议：添加、编辑和保存凭据本身不提交认证；“保存”和“切换并登录”使用清晰、不同的操作名称。

### 2. 设置页顶部展示账号

设置标题下第一块就是“校园账号”，显示已保存账号、当前选用账号、密码配置状态，以及添加、编辑、切换和删除入口。外观、启动、提醒、更新等设置排在其后。

概览页同时保留明显的账号管理入口，未配置时可直接前往设置。

### 3. 首次使用引导

- 首次使用明确说明：“需要在助手中保存校园网账号和密码，才能使用自动登录。”
- 提供“设置账号”和“暂时跳过”，允许不保存密码而查看网络状态。
- 设置凭据后，再解释并提供“开机自启”和“启动时自动登录”的选择；保存成功不能直接显示为登录成功。
- 跳过后不反复弹出完整引导，但主页和设置页保留未配置提示。
- 从旧版升级且已有凭据的用户不应被当作完全未配置的新用户。
- 凭据损坏或无法解密时明确显示读取失败，提供重新配置入口，不伪装成正常未设置。

### 4. 网络状态与凭据状态分开呈现

| 实际网络 | 软件凭据 | 界面含义 |
| --- | --- | --- |
| 已在线 | 未保存 | 校园网已登录，但助手尚未保存账号密码，无法代为自动登录 |
| 未登录 | 未保存 | 当前未登录；可设置账号后由助手登录，也可前往官网自行登录 |
| 已在线 | 已保存且身份一致 | 显示当前在线账号；另行显示启动登录设置 |
| 已在线 | 已保存但身份不同 | 分别列出当前在线账号和当前选用账号，提供明确切换入口 |
| 未登录 | 已保存 | 可以手动登录；是否启动时登录由设置决定 |
| 查询失败 | 任意 | 网络状态暂时无法确认，不将查询失败当作已离线 |

无凭据但在线的建议文案：

> 校园网已登录。你尚未在助手中保存账号和密码；当前连接可能是在 go.ruc.edu.cn 或其他方式完成的。若要使用助手自动登录，请先设置账号。

只能说“可能”，不能断言本次连接来自官网。状态检测无需凭据；需要认证的操作应说明前置条件。

### 5. 自动登录行为简化

明确目标：开机后启动软件，由软件完成登录；用户主动下线后保持下线，不需要理解或操作“自动登录暂停”。

建议将“自动登录”收敛为“启动时自动登录”：

| 触发场景 | 建议行为 |
| --- | --- |
| 登录 Windows，且开启开机自启 | 程序在托盘启动；开启启动登录且有有效凭据时检查并登录 |
| 手动启动程序 | 同样遵循启动登录设置，此规则待确认 |
| 启动时校园网络暂未就绪 | 保留本次启动登录任务，在网络就绪后有限重试；超出约定窗口后提示失败 |
| 已在线且账号一致 | 保持连接，不重复提交认证 |
| 已在线但账号不同 | 提示差异，不自动注销；用户点击切换后才更换认证 |
| 用户主动下线 | 结束本次启动登录任务及待重试请求，保持离线；启动登录设置不因此关闭 |
| 下线后点击登录或切换账号 | 执行这次明确操作 |
| 成功登录后意外断网、官网下线或休眠唤醒 | 建议继续检测状态，不自动重新认证，此规则待确认 |
| 完整退出后重新启动程序 | 视为新一次启动；关闭窗口后从托盘重新打开不算新启动 |
| 密码错误、欠费或账号限制 | 显示具体原因与处理入口，不持续提交失败认证 |

不再暴露“自动登录已暂停”“点击连接恢复自动登录”等状态。正常手动下线直接显示“已下线”。启动登录失败、未配置凭据、账号不一致分别说明实际原因。

如果采用上述建议，“休眠唤醒后恢复连接”也应删除，而非仅隐藏暂停文案。内部仍需防止旧请求在主动下线后重新认证，但这属于操作协调，不再是用户管理的功能状态。

## 四、连带影响与范围

- 当前低流量提醒依赖自动登录后台循环。简化登录后，应让网络查询和提醒独立工作，不能随重连逻辑一起失效。
- 设备档案已有按账号隔离机制；切换时还需清理旧请求、统计缓存和界面焦点，保证数据归属一致。
- 删除本地凭据不等于注销网络。建议删除时明确说明；删除选用账号后要求选择其他账号，不静默切换并登录。
- 主题、自启动等通用设置建议继续全局保存；启动登录使用当前选用账号。
- 本次不增加云同步、Windows 多用户隔离体系或远程设备自动踢下线能力。
- 后续实现应同步修改首页、设置页、托盘相关行为、使用说明与必要验证；本阶段不更改功能和版本号。

## 五、核心验收场景

1. 无凭据首次打开时可以跳过引导，并正确看到网络已在线，同时明确知道软件未保存密码。
2. 设置页第一块即可设置和管理账号，保存成功与网络登录成功有独立反馈。
3. 已在线 A 切换 B 后，只有接口确认本机在线身份为 B 才显示切换成功。
4. 注销失败、密码错误、超时和重复点击不会导致界面假成功、后台抢回旧账号或串账号展示数据。
5. 保存但未登录、外部网页登录、接口查询失败，都有准确且不同的状态说明。
6. 开机自启与启动登录分别可设置；没有凭据时无法开启启动登录且有直接配置入口。
7. 手动下线后，包括待处理的启动重试在内，都不能把用户重新连回去；界面不显示“暂停”。
8. 从 1.1.0 升级后凭据、账号对应设备名称与通用设置可以继续使用；旧暂停状态不进入新交互。
9. 简化自动登录后，无凭据查询和低流量提醒仍按各自条件工作。

## 六、实现前需要确认的关键规则

1. 自动登录是否严格限定在每次程序启动，成功后不再因意外断网或唤醒自动重连？建议是。
2. 手动启动程序是否也触发启动登录，而不仅限于 Windows 开机自启？建议是。

其余细节可按文中建议形成实现方案；启动重试次数、间隔和最长等待窗口在实现设计时明确。
