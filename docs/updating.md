# GitHub 自动更新设计

状态：设计方案，尚未接入客户端。保持 Windows 便携版形态，不生成安装包。

## 用户体验

设置页在现有版本号附近增加“软件更新”区域：

```text
软件更新
当前版本 1.0.0                         检查更新
自动检查更新                           [开关]
更新网络                               跟随系统代理 ▾
上次检查：今天 14:30
```

默认开启自动检查，仅检查版本，不自动下载、退出或替换程序。更新网络默认“跟随系统代理”，另提供“直接连接”。该选项只影响软件更新。

发现新版本后，在区域内显示版本号、发布日期、下载大小、简短更新说明，以及“下载更新”“查看发布说明”“暂不更新”。后台运行时，同一版本最多发一次系统通知；通知点击后打开更新区域，不强制弹出主窗口。“暂不更新”停止该版本的主动提醒，手动检查仍可看到它。

下载时显示进度与取消按钮；校验成功后显示“重启并更新”和“稍后”。稍后不会在用户下一次退出时偷偷安装，重新打开仍可主动更新。替换前明确提示将短暂关闭助手，账号、设置与设备名称会保留。

状态包括：未检查、检查中、已是最新、发现新版、下载中、校验中、待重启、更新中、失败。失败保留原程序和重试入口，不以“已是最新版本”掩盖网络错误。更新失败不影响校园网登录和统计。

## 检查时机

- 启动后延迟约 30 秒检查，避免与校园网登录争抢启动阶段资源。
- 没有可用网络时延后，校园网连接成功后可再检查；一天内自动检查最多一次成功结果。
- 持续运行时每天检查一次，附加少量随机延迟；手动检查不受每日间隔限制，但限制连续点击。
- 失败采用有上限的退避；代理设置改变后，手动重试立即重新读取设置。
- 使用 ETag/条件请求缓存。遇到限流尊重 GitHub 返回的重试时间，不持续轮询。
- 第一版仅接受正式版；比较 SemVer，不能用字符串大小比较版本号，不自动降级。

## 网络必须分开

| 请求 | 连接方式 | 身份与数据 |
| --- | --- | --- |
| 校园网登录、注销、流量、会话、设备 | 固定直连 | 保留现有校园网专用 Cookie 与凭据 |
| GitHub 版本检查、更新说明、清单、签名、程序下载 | 默认跟随 Windows 当前用户系统代理 | 不使用校园网 Cookie，不携带学工号、密码、设备档案 |

现有 `portal.rs` 的 `Client::builder().no_proxy()` 保持不变，包括禁用环境变量代理。不设置进程级 `HTTP_PROXY` 等变量，不把更新客户端注入校园网模块，不让前端 WebView 直接下载更新。

### 更新网络的具体实现

建议增加独立 `update_network.rs`，使用 Windows WinHTTP 完成更新请求。默认读取当前登录用户的 Windows 代理配置，而不是只读取管理员配置的 WinHTTP 机器代理。

1. 通过 `WinHttpGetIEProxyConfigForCurrentUser` 获取手动代理、绕过列表、自动配置脚本与自动发现配置。
2. 手动代理按 Windows 配置使用；PAC/WPAD 通过 `WinHttpGetProxyForUrl` 按目标 URL 解析，尊重脚本给出的代理或 DIRECT 结果。
3. 对 GitHub 下载重定向的每一个目标重新应用代理策略；限制重定向次数，仅允许 HTTPS 和审核过的 GitHub API、Release、资产下载域名。不能只代理 API 检查而让实际下载直连。
4. 每次新的检查/下载重新读取配置。用户刚开启代理后无需重启助手；进行中的下载可以取消后重试。
5. 系统未配置代理时正常直连；已配置代理但连接失败时显示“无法连接更新服务，请检查系统代理或稍后重试”，不自动绕过代理。PAC 解析失败也应显示错误；PAC 明确返回 DIRECT 则允许直连。
6. 用户主动选择“直接连接”时，更新请求显式禁用系统与环境代理。HTTPS 证书验证始终开启。

不建议仅因 reqwest 有自动代理能力就认定它覆盖了完整 Windows 系统配置：当前项目使用 reqwest 0.12.28 且关闭默认 features；该版本将 `system-proxy` 列在默认 features 中，当前未显式启用。即使补上 feature，也须独立验证 PAC 与重定向行为。因此采用明确的 Windows 代理解析路径，减少依赖隐式默认值。

本方案的“校园网直连”指应用不使用 HTTP/SOCKS 系统代理。VPN/TUN、路由表与代理软件的透明接管在操作系统层生效，`.no_proxy()` 无法强制绕过；使用这类模式时，需要在代理工具中为校园网域名及相关网段设置直连规则。程序不修改用户的代理工具配置。

## GitHub Release 约定

使用公开仓库 `FengNKT/ruc-web-helper`，无需客户端登录 GitHub，也不在软件中内置 GitHub token。仓库 owner/repo 和更新公钥在发布时固定到程序中，不作为普通用户可随意修改的更新地址。

通过 `GET https://api.github.com/repos/{owner}/{repo}/releases/latest` 查找正式 Release。读取 tag、说明和附件，确认不是 draft/prerelease；去掉 tag 的单个 `v` 前缀后用 SemVer 解析。GitHub 对 latest 的判定不等于求所有 tag 的 SemVer 最大值，因此发布流程必须正确维护正式版及 Latest 标记；客户端始终拒绝低于当前版本的自动更新。

每个正式 Release 应提供：

```text
ruc-web-helper_<版本>_windows-x86_64_portable.zip   首次下载使用
ruc-web-helper_<版本>_windows-x86_64.exe            应用内更新使用
update.json                                       更新清单
update.json.sig                                   清单的数字签名
```

第一版只发布实际支持的架构，不根据操作系统架构猜测包类型，应以当前程序构建目标匹配；将来支持 ARM64 时在清单中添加独立目标。不要把 GitHub 自动生成的 Source code 压缩包当成程序更新包。

更新清单至少包含：格式版本、项目标识、SemVer 版本、tag、发布时间、最低更新器版本，以及按目标划分的资产名、固定 tag 的下载 URL、字节数与 SHA-256。更新说明可使用 Release 正文，但按纯文本呈现并限制长度，不执行 HTML。资产缺失、版本不匹配或清单格式未知时，提示“该版本暂不支持应用内更新”，提供 Release 页面入口。

### 校验方式

发布流程使用独立 Ed25519 更新签名密钥，为 `update.json` 的原始 UTF-8 字节生成分离签名。客户端内置公钥，先验证清单签名，再读取受签名保护的版本、平台、大小和程序摘要。下载后流式计算 SHA-256，并在替换前再次校验。

签名失败、大小超限、平台错误、摘要不符一律不执行。SHA256.txt 或 API 中的摘要可以辅助诊断，但不能替代发布者签名。私钥不进入仓库、Release 或客户端；GitHub Actions 中放入受保护的 Secrets，并保留离线备份。第一版采用固定公钥；更换密钥需提前发布信任新公钥的过渡版本。

## 便携版怎样完成替换

Tauri 官方 Windows updater 使用 MSI/NSIS 安装产物，与当前无需安装的便携 EXE 路线不同。本项目采用独立的便携更新逻辑，不直接套用安装器更新流程。

下载暂存与更新状态放在程序目录的 `.updates/`，仅替换正在运行的 EXE，保留其实际文件名和路径。不能用 Release 中的英文资产名覆盖本地中文命名习惯；这样开机自启路径也保持有效。

流程为：

```text
检查新版 → 用户下载 → 校验签名与程序
    → 等待用户点击“重启并更新”
    → 启动独立更新助手 → 主程序完整退出
    → 备份旧 EXE → 同卷替换 EXE → 启动新版
    → 新版确认初始化成功 → 标记完成
```

更新助手可复用现有 Rust EXE：把当前程序复制到 `.updates/` 中，以内部 `--apply-update` 模式启动。该分支必须在 Tauri 初始化、单实例检查、托盘与自动登录任务之前执行；以隐藏窗口启动，避免出现命令行窗口。只接受主程序生成的受限更新任务，前端不能传任意目标路径或任意下载 URL。

助手需要持有原进程句柄并等待其完全退出，不能只等窗口关闭，也不能只用可能被复用的 PID 判断。应用退出不会主动注销校园网；连接通常可保持，但不承诺网络在重启期间绝对不中断。

替换前确认目录可写、磁盘空间充足、下载文件完整、目标解析后的绝对路径和预期当前 EXE 一致，拒绝重解析点造成的目录逃逸。若程序仍被占用则有限重试，不强杀进程，不自动提权。失败恢复旧 EXE，并留下下次打开可见的结果；不要求用户删除原程序。

更新任务以原子写入的日志记录阶段，处理断电或助手异常退出后的恢复。新版使用任务标识通过本地握手确认核心初始化成功；超时不能直接覆盖仍运行的新版，需要先请求其退出并确认进程结束，再恢复备份。系统性能较慢时提供重试，避免把缓慢启动误判为永久失败。只保留一份已知可用的旧 EXE，成功确认前不删除它。

不覆盖 `account.enc`、`settings.json`、`devices.json`、WebView2 数据目录。将来的数据格式迁移需要向后兼容；无法兼容的迁移必须先备份受影响文件并设计对应恢复步骤，不能只恢复 EXE 就声称完整回滚。

## 发布者的操作

配置好首次仓库地址和签名密钥后，建议由 GitHub Actions 在版本 tag 推送时：

1. 检查各版本清单一致，运行现有离线检查，使用干净环境构建便携 EXE。
2. 生成首次使用 ZIP 与独立更新 EXE；计算大小、摘要，生成并签名清单。
3. 创建草稿 Release，上传所有附件，并核对清单引用的资产。
4. 通过完整性检查后发布正式 Release，更新说明使用面向用户的文字。

只有包含规定附件且签名正确的 Release 才能应用内更新。普通手动上传 EXE 而不生成清单和签名，只能供手动下载。发布与更新仓库不包含任何日常使用账号或配置。

## 实现范围与验证

建议新增 `update.rs`（状态机与校验）、`update_network.rs`（系统代理和下载）、`update_apply.rs`（替换与恢复）、发布脚本及 GitHub Actions 工作流。UI 只调用检查、下载、取消、应用更新命令，通过事件接收进度。后台更新任务与校园网任务使用独立锁，不能让下载占用现有登录服务锁。

验证应覆盖：

- 配置本地测试代理后，更新请求到达代理，校园网模拟服务器请求直达且无代理访问记录；分别覆盖环境变量代理、手动系统代理、PAC、下载重定向。
- 下载时代理切换、超时、取消、断网、限流、无正式 Release、缺失附件等情况。
- 旧版本/预发布版、损坏签名、错误架构、错误摘要、超大响应、非 HTTPS 重定向。
- 含中文和空格的路径、自定义 EXE 名、目录不可写、文件占用、进程未退出、替换中断及恢复。
- 更新后账号与设备命名保留，开机自启仍有效，回滚有明确结果；测试只使用虚构本地数据。

第一版不加入镜像站、增量更新、静默安装、强制更新或测试版渠道。提供“打开发布页面”作为手动更新后备入口。

GitHub 仓库已确定为 `https://github.com/FengNKT/ruc-web-helper`，真正上线前仍需实现客户端更新逻辑并生成签名公钥。首发 1.0.0 尚未包含更新逻辑，不能自动感知未来版本；用户至少需要手动换到首个支持更新的版本一次。
